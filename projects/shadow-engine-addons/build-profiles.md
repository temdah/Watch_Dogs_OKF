# What the archive experiments established

Shadow Engine Addons provided a case study in modifying database and world-light
assets while proving that unrelated data stayed intact. Its vehicle payload used
seven approved inputs; optional world lighting was rebuilt independently from
verified retail data. Two editions sharing a runtime were checked for identical
common assets and ASI/Lua bytes. These are build controls, not engine guarantees.

The public vehicle-reference repair changed only the affected preset LIB.
Six other base assets and the FAT/NFO controls remained unchanged. The world
experiment enabled 12,788 audited caster flags in 1,883 batches. A separate
lower-lamp experiment retained 80 definitions at their original shadow-off value;
see [world-batch mapping](world-light-shadow-batches.md) and
[targeted exclusions](secondary-streetlamp-shadows.md).

# Compare the actual package

A source-file hash or successful pack command is insufficient. The validation
re-opened the produced DAT/FAT/NFO and ZIP, checked membership and bytes against
inputs, then exported real LIB/FCB data for independent semantic comparison.
Alternative payloads used isolated staging so one profile could not silently
reuse another profile's generated files. See
[semantic reference validation](established-feature-tests.md).

Hidden menu entries did not exclude experimental native code. An explicit
compilation/include allowlist and final PE-export/diagnostic-marker checks
separated a production host from optional observers. The shared scheduler was
tested with and without observer callbacks; observer storage did not own native
resources. [Storm host isolation](public-storm-runtime.md) describes that boundary.

# Toolchain failure that a help probe missed

Compressed world extraction required the allowlisted XNA native DLL and its
extracted 32-bit VC runtime. The extractor could pass startup/help probes while
real compressed extraction failed. Supplying the runtime directory in the child
process search path, then restoring the environment, repaired that dependency.
Actual extraction followed by independent retail-byte comparison was the useful
compatibility check. No system registration or tool rebuild was needed.

# Evidence limits

These checks established the inspected files, references and compilation boundary.
They did not establish mod-manager merge order, live menu coexistence, wet-road
appearance, shader selection, resource readiness or runtime performance.
Exact build commands and delivery choices belong to the mod's build instructions;
the reusable lessons here concern archive integrity and controlled experiments.

# Addons-specific regional boundary

[Regional native compatibility](native-compatibility.md) records the five-build
code/layout proofs and recursive Lua prototype limits. A provider mod passing its
own corpus is insufficient. Public/internal compilation and asset semantic gates
remain independent, and offline acceptance is separate from game observations.
